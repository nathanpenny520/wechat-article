# 整合与优化说明

本文说明这次整合做了什么、为什么这样做、放弃了什么、以及还剩哪些没做完。

## 一、整合前的两个项目

| | 项目 A | 项目 B |
|---|---|---|
| 仓库 | `imraywang/wewrite` | `aiworkskills/wechat-article-skills` |
| License | MIT | Apache-2.0 |
| 形态 | 1 个主入口 + 9 个模块 skill + 一个 pip CLI | 9 个 skill + 每 skill 自带脚本 |
| 强项 | 内容质量纪律（任务书 / 主张证据 / 编辑门槛）、任务状态机、18 套主题与微信兼容自动修复、学习飞轮、数据复盘、多平台改写 | 视觉方法（封面七步推导 + 12 封面形态 + 8 正文形态 + 媒介轮换）、版式组件层、审稿的 AI 味指纹库、业务资料库、发布的封面裁剪框与多账号 |
| 弱项 | 排版缺文档外层容器、CJK 预处理会破坏行内代码与链接、嵌套列表丢层级；发布缺封面裁剪框、多账号、压缩与重试 | 无任务状态机（每步停下确认的代价）、无学习飞轮与数据复盘、无统一 CLI、排版与生成的两层配置分散 |

**两者的能力几乎不重叠，重叠的三处（排版 / 发布 / 生图）经代码级对比后各有所长。** 这是整合能成立的前提。

## 二、整合后的形态

一个自包含 skill：`wechat-article/`

```
wechat-article/
├── SKILL.md                     # 唯一入口：路由 + 全流程编排 + 门禁
├── references/                  # 14 份阶段文档，按需加载
│   ├── 00-workflow.md           # 状态契约 / 门禁 / 恢复 / 两引擎分工
│   ├── 01-setup.md              # 安装、自检、首次配置、排障
│   ├── 02-topic.md 03-write.md 04-review.md
│   ├── 05-format.md 06-visual.md 07-publish.md
│   ├── 10-learn.md 11-stats.md 12-rewrite.md 13-products.md
│   └── 20-wechat-html-constraints.md 21-quality-rubric.md
├── scripts/                     # 运行时（自包含，无需 pip install 本项目）
│   ├── wxart.py                 # 统一 CLI 调度器
│   ├── wxenv.py                 # 路径 / 状态 / 配置统一解析
│   ├── wxguard.py               # 引擎容器栅栏 + 产物门禁
│   ├── wxengine/                # 项目 A 的运行时代码（改名内嵌）
│   └── aws/                     # 项目 B 的运行时代码（保留上游布局）
├── assets/                      # 7 套写作人格、2 个平台定义
├── templates/ tests/ install.sh VERSION
```

四个动作把两个项目变成了一个 skill：

### 1. 一个入口，一套工作流

原来 A 说「写一篇」、B 说「帮我写篇公众号文章」，各自有自己的流程与状态。现在只有一份 SKILL.md，
一条 7 步主流程，一套硬门禁。两个项目里重复的选题 / 写作 / 审稿 / 排版 / 配图 / 发布**合并成一份方法**，
而不是并列两套。

### 2. 一个 CLI，三个引擎开关

```bash
python3 {skill_dir}/scripts/wxart.py <命令>       # 简写 wxart
```

命令按阶段分组（环境 / 选题 / 写作 / 排版 / 配图 / 发布 / 学习 / 复盘 / 资料库 / 任务），
三个重叠能力用 `--engine` 切换，默认值按各自长处选：

| 能力 | 默认 | 为什么 |
|---|---|---|
| 排版 | `wx` | 18 套主题开箱可用；外链脚注、CJK 间距、加粗标点、列表转换、暗黑模式、粘贴加固全是自动的；有 `validate` 校验 |
| 配图 | `aws` | 比例走结构化参数 + 后置居中裁切且默认不裁；出图后有尺寸 / 近单色的确定性检查；prompt 文件带 frontmatter |
| 发布 | `aws` | 多账号槽位、封面裁剪框（2.35:1 + 1:1）、图片自动压缩、`publish_method` 抽象、网络重试与可调超时 |

### 3. 一套状态与配置

这是整合里最关键的一处工程决定。两个项目原本互不相容：

| | 项目 A | 项目 B |
|---|---|---|
| 用户状态 | `~/.wewrite/` | 工作区 `.aws-article/` |
| 密钥 | 写进 `config.yaml` 或环境变量 | 工作区根 `aws.env`，与配置分离 |
| 每篇状态 | `runs/<run_id>/state.yaml` 任务机 | 每篇 `article.yaml` 文章元数据 |
| 主题查找 | `~/.wewrite/themes/` | 项目 `.aws-article/presets/formatting/` → `~/.aws-article/…` → 内置 |

收敛后的模型（**不改动任何上游代码**）：

```
~/.wxarticle/                     ← 唯一的状态与配置真源（$WXARTICLE_HOME 可覆盖）
├── config.yaml  .env  style.yaml  history.yaml  playbook.md
├── runs/<run_id>/                ← 一篇文章 = 一个任务目录，两个引擎共用
├── presets/  products/  exemplars/  lessons/  themes/  personas/  corpus/
<工作区>/.aws-article  ──软链──▶  ~/.wxarticle/      （可选的项目覆盖层同理）
```

- 项目 A 的引擎用 `WEWRITE_HOME` 环境变量指到 `~/.wxarticle/`（一行，零改动）。
- 项目 B 的引擎按 CWD 相对路径找 `.aws-article/`，于是 `wxart` 在真正执行的目录建一个**软链**指向
  同一个配置目录。上游写死的 `repo/.aws-article/{config.yaml,presets,products,tmp}` 全部落到同一条路径上。
- 密钥查找顺序：配置目录 → 工作区根 → 状态目录（`aws.env` 与 `.env` 都认）。
- 需要「一个仓库一个公众号」时，才在工作区建真实的 `.wxarticle/` 作为项目覆盖层。

### 4. 一篇文章一个目录，两个引擎共用

`~/.wxarticle/runs/<run_id>/` 里同时存放两套引擎的产物：任务状态与内容质量产物
（`state.yaml` / `brief.yaml` / `claims.yaml` / `draft.md` / `review-report.json` / `article.md`）
与发文产物（`article.yaml` / `article.html` / `cover.png` / `imgs/`）。这是「整合」在文件系统层面的落实。

## 三、优化点（整合之外新做的工程）

### 1. 把静默的语义漂移变成显式报错 ⭐

两个排版引擎的 `:::` 容器**部分同名但语义不同**：

| 容器 | wx 引擎 | aws 引擎 |
|---|---|---|
| `steps` | 每行一步，自动编号、无参数 | `:::steps[标题]`，每行「步骤名 \| 说明」两列 |
| `highlight` | 琥珀色盒 | 已废弃，退化成普通文本 |

同一份 Markdown 在两个引擎下渲染成完全不同的结构，**而且不会报错**。这是整合中最危险的一类坑。

新增 `scripts/wxguard.py`，并让 `wxart format` 自带两道栅栏：

- **排版前**：扫描 `:::` 块，出现只属于另一个引擎的容器、`steps` 写法不符、或缺结尾 `:::` →
  中止并打印行号与期望写法（退出码 4，`--force` 可跳过）。
- **排版后**：对产物跑微信兼容门禁（退出码 5，`--no-check` 可跳过）。

`steps` 的两种写法靠「有没有方括号参数 / 行内有没有 `|`」判定，因此同名冲突也能被识别。

### 2. 补上「校验并不阻断」这个缺口

项目 A 的文档声称 preview/publish 会「拦截」会被微信过滤的写法，实际上它只把 `⚠` 打到 stderr，
不影响退出码。现在 `wxart format` 在排版后**自动跑门禁并按退出码判定**，门禁成了真门禁。

门禁有两个口径，因为两个引擎的合法产物不同：

- `profile=wx`：完整规则（含 `div` / `class` / `id`）。
- `profile=generic`：`div` / `class` / `id` 降级为提示——aws 引擎会为微信专有嵌入类型输出
  `class`（`normal_text_link` 等），也会用 `<div>` 做分隔，按 wx 口径判会误报。

规则表直接复用随 skill 内嵌的引擎规则（16 条），不另抄一份，避免两处规则漂移。

### 3. 命令层面的一致性修复

- `wxart format` 走 wx 引擎时自动加 `--no-open`，不再在 Agent 流程里弹浏览器。
- `wxart doctor` 把两个项目的自检合**成一份八类检查**，并明确区分「阻塞 / 提示」——
  缺写作模型、缺画图模型、缺微信凭证都只提示，不阻断写作、排版与配图。
- `wxart env` 打印每一份实际读到的文件路径，配置读错地方一眼可见。
- 退出码语义统一：`2` 参数错误 / `3` 环境或依赖不可用 / `4` 容器与引擎不相容 / `5` 产物未过门禁。
- 上游把生图的「图片模型未配置（2）」与「跑错目录（1）」分开，这个区分在文档里也写明了，
  避免 Agent 把环境错误当降级信号。

### 4. 消除品牌混装

内嵌的 A 引擎包改名为 `wxengine`，`_COMMANDS` 里的模块路径同步改掉。
用户可见的文档里不再出现上游品牌名（发布/迁移必须点名的历史路径与预设包下载域名除外）。

### 5. 内容质量纪律来自 A，视觉方法来自 B，都进了同一套门禁

- 来自 A：任务书 → 主张与证据 → 初稿的**顺序不可颠倒**；五项编辑判断与
  「平均 ≥4、单项 ≥3、无阻断」门槛；最多两轮；`publishable=true` 才能写成 `article.md`；
  封存后原始正文只读；单次人工修改永远是软参考。
- 来自 B：`{embed:…}` 文末元素的四类规则、摘要不得与导语逐字相同、AI 味默认只诊断不阻断、
  敏感词与自定义审稿规则、业务资料库必须先读后用。
- 发布门禁合并成四条（HTML 已由当前正文生成 / 封面在文章目录根 / 无 `placeholder` / 明确授权），
  并明确「拿到回执才写 `publish_completed: true`，否则只报『草稿已提交，正文配图未完成』」。

## 四、明确的取舍

| 决定 | 理由 | 代价 |
|---|---|---|
| 保留两个排版引擎，不强行合并 | 合并需要把 A 的容器体系重建在 B 上（或反之），估算 63–85 人时的架构级改造，且会同时丢掉 A 的暗黑模式或 B 的组件数据化能力 | 用户需要理解「换引擎要重跑」，容器语法按引擎分表 |
| 排版默认 wx 引擎 | 18 套主题与自动微信修复开箱可用，不需要先做主题格式转换 | 设计表现力不如 aws 的模版×配色 + 组件层，后者需要显式 `--engine aws` |
| 不做容器语法的双向自动翻译 | 语义不是一对一（`steps` 同名异义、`highlight` 已废弃、`callout` 在 B 没有对应物），自动翻译会制造新的静默错误 | 换引擎时要人工调整含 `:::` 的段落，栅栏会提前报错 |
| 状态收敛到 `~/.wxarticle/`，工作区用软链 | 上游代码零改动即可共用同一份配置；这是最低风险的收敛方式 | 工作区里会出现一个隐藏软链 `.aws-article`；Windows 上退化为真实目录 |
| 保留 `state.yaml` 作为任务真源 | A 的任务机含步骤状态与发布授权，B 完全没有这层；门禁与恢复都依赖它 | 与 `article.yaml` 有字段重叠，文档里必须说清各自职责 |
| 不移植 A 的 10 个 provider 抽象到 B 的生图路径 | 是「按 provider 重写协议层 + 逐个活体冒烟」的活，估算 29–38 人时；默认路径用 B 的引擎已经够 | wx 引擎的多 provider fallback 只能在 `--engine wx` 时用 |

## 五、还没做完的（按价值排序）

1. **把 aws 引擎的组件层接进默认排版路径**。现在要 `--engine aws` 才能用「模版 × 配色 + 版式组件」，
   而写稿阶段默认按 wx 容器写。若把 B 的组件加载器与钩子系统移植到 A 的转换器
   （估算 41–59 人时），就能用一套语法吃两边的表现力，同时消掉「换引擎要重跑」。
2. **封面链路统一**。A 生图的 cover 预设多数 provider 是 1.75:1 且不提交裁剪框，B 是 2.35:1 + 裁剪框。
   现在默认走 B 所以没问题，但 `wxart image --engine wx` 出的封面应自动补裁剪框。
3. **规则表与渲染一致性的自动化守护**。A 的 `write.py` 与转换器各有一份金句正则，
   历史上漂过一次（检查放行、排版渲染失败）。这类跨模块判据需要测试断言。
4. **`wxart run` 与发布的接线**。A 的发布路径原本不读 `permissions.publish`；
   现在默认走 B 的发布栈，授权由 SKILL.md 与门禁强制，但 CLI 层没有硬绑定。
5. **容器语法迁移检查器**。栅栏能拦住写错引擎，但存量文章从旧项目迁过来时，只能一个一个块看报错。
6. **图纹背景——已补上（`wxart deco`）**。2026-10-04 探针实测：`background-image` 用**外部链接会被微信整条删掉**，
   `<section>` 还在、声明没了；其余内联样式（渐变、flex、圆角、阴影、内联 SVG）逐字节保留。
   第三批探针进一步确认：换成**微信图床链接（`mmbiz.qpic.cn`）后 `background-image` 连同
   `repeat` / `size` / `position` 全部保留**。所以链路是「本地位图 → `media/uploadimg` 换链接 →
   写进 `background-image`」，`wxart deco` 已按这条链路实现（纸纹底 + 花边框，主色自动从产物里认）。
   实测依据见 [../wechat-article/references/20-wechat-html-constraints.md](../wechat-article/references/20-wechat-html-constraints.md) 第 3 节。

### 2026-10-04 第二轮：文档、配图、皮肤

- **`wxart docs`**：官方文档本地镜像（`fetch` / `search` / `show`）。以前接口规定靠探针一条条试，
  试出来的只覆盖试过的那些。镜像落在**状态目录、不进版本库**（内容版权归腾讯），
  仓库里只放抓取脚本 + 我们自己写的 `references/22-wechat-api-reference.md`（只收本流水线依赖的规定）。
  镜像当场就证实了探针结论：官方原文写着正文图片「必须来源上传接口，外部图片 url 将被过滤」。
- **`wxart chart`**：把文章里**已经核实过的数字**画成正文配图（`bar` / `kpi` / `timeline` / `compare`）。
  没有生图模型时这是唯一诚实可行的配图方式——它不推算任何数据，只渲染 spec 给的数字，
  并支持 `source` 把出处印在图上（图表的视觉权威感会让读者默认它是硬事实）。
- **`wxart doctor` 增加 `docs.mirror` 检查（`info` 级）**：没抓官方文档时给一条可选建议，
  抓过则显示页数。为此给 doctor 加了第三个级别 `info`——原来只有 ok / warn / error，
  而这个建议判成 warn 会把「全部通过」改成「N 项提示」，等于把可选项算进待处理清单。
  `info` 单独计数、**不改变退出码**；doctor 也不做交互式询问（它被 Agent 与脚本非交互调用，
  卡在 `input()` 上比少问一句严重得多）。
- **`make_deco` 拆成「底子 × 花边」两维**：底子 `dot` / `grid` / `kraft`，
  花边 `none` / `single` / `double`，八个预设皮肤由两维组合而成。
  新增 `--texture` / `--frame` 可单独覆盖预设。
- **配图带动了 `img-deco`**：正文有图之后，骨架自带的图片装饰开始生效
  （硬朗给双色块、活力给渐变条、手账给斜贴胶带）。此前两篇都没图，这一层装饰一直没触发。

### 2026-10-04 本轮补上的

- **`wxart shot`**：把排版产物截成 375px 手机宽度 PNG（并可多主题拼对照图），
  顺带报横向溢出。此前所有门禁只验 HTML 的**正确性**，观感没有一条在验——
  「主题没选对、标题折行难看」会一路通过门禁直到人打开草稿箱才发现。
- **`wxart redraft`**：走 `draft/update` **原地更新**已进草稿箱的稿子。
  此前换一次模版就多一条草稿，试三套模版草稿箱里就多三条近乎重复的稿子。
- **`wxart deco`**：纸纹底 + 花边框。先把底图传到微信图床换 `mmbiz` 链接，
  再写进 `background-image`——这是微信唯一认的背景写法。装饰一律加在**外层容器**上，
  不猜正文内部结构（标题被 `h2-deco` 包在 `display:flex` 行里，事后插入会插进 flex 行内部）。
  四角装饰直接用 `border-radius`，因为定位所需的 `position` 会被微信整条删掉。
- **`:::aside` 旁注组件**：补上 aws 侧缺的「提示框」。
  刻意不复用 wx 的 `callout`——两者方括号参数语义不同（wx 是固定类型关键字，
  aws 是自由标签），同名不同语义正是容器栅栏要拦的东西。
- **中文序号与编号骨架的双编号**：编号骨架的 `h2-deco` 会自动加 `01`，
  而正文标题常写着「一、」。两边都留就是「01 一、先说那脚刹车」。换到编号骨架时要先去掉中文序号。
- 新增 23 条测试（`aside` 栅栏与渲染、`shot` 宽度与溢出判定、`redraft` 的离线 `--dry-run`、
  `deco` 的主色识别与「没有凭证时必须失败而不是悄悄内联 `data:` URI」、底图生成的确定性与平铺周期、
  以及「内置组件与栅栏容器集合必须恰好相等」的一致性断言）。
- 顺带修掉一个**会在正蓝主题上咬人的隐性 bug**：主色识别原本用「亮度 > 0.95 判近白」，
  把 `#2E7BF6` 这类又亮又饱和的正蓝一并丢掉，主色一丢就退回兜底红、装饰与主题当场脱节。
  判中性色只能看饱和度。

## 六、验证方式

```bash
bash wechat-article/tests/run.sh
```

- `test_contracts`：主入口的 frontmatter 与触发边界、四道硬门禁是否写在 SKILL.md 里、
